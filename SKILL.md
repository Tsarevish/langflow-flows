# Работа с Langflow

Собирай граф, соответствующий задаче пользователя, и проверяй его поведение.
Для анализа без правок читай данные, не создавай и не запускай флоу.

## Контекст и вопросы

Используй сведения текущей задачи, выбранного подключения и подтверждённого профиля.
Если целевой стенд однозначно известен, назови его и продолжай. Иначе спроси
адрес/подключение либо предложи офлайн. Не выбирай другой стенд и не переноси его ключи.
Сохраняй модель и параметры существующего графа, если задача их не меняет.
Для нового графа можно взять подтверждённую рабочую модель целевого профиля, назвав выбор.
Спрашивай о модели, входе/выходе, данных и архитектуре только при отсутствии сведений,
когда решение существенно влияет на результат. Объединяй связанные вопросы и предлагай
2–3 варианта с рекомендацией. Рутинные обратимые решения принимай самостоятельно.
Если необходимы адрес, доступ или решение о внешней записи, дождись ответа.
Молчание не означает согласия. Необязательное допущение можно назвать и продолжить.
Поручение выполнить работу разрешает необходимые действия в его рамках:
отдельное подтверждение обычного плана не требуется.

## Режим и схема стенда

- **Live:** есть инструменты сборки MCP или REST. Проверь реальный список tools:
  префикс зависит от подключения. MCP, публикующий готовые флоу как tools,
  может не предоставлять инструментов сборки.
- **Offline:** выдай `.spec`, зависимости и инструкцию проверки. Скажи:
  «спека не проверена на инстансе». Без снапшота нельзя подтвердить даже порты.
  Не обещай JSON для импорта: spec не является экспортом Langflow.

Профиль: `profiles/<стенд>/profile.md` — ручные настройки; `profile.auto.md` и
`profile.json` — разведка; `components.json` — схема. Сопоставь URL и версию с целью.
Обновляй схему и после изменения расширений без смены версии.
Снять профиль: `python scripts/probe_stand.py --url <URL>`.
Ключ передавай через `LANGFLOW_API_KEY` или защищённый локальный env-файл,
не проси вставлять его в чат. Поддерживаются `LANGFLOW_URL`/`LANGFLOW_SERVER_URL`.
Повторная разведка сохраняет ручной Markdown, `limits`, `quirks` и дополнительные поля JSON.
Неудачная загрузка схем не заменяет предыдущий снимок.

В Live не придумывай имена типов, портов и полей. Получи `describe_component_type` один раз
для каждого используемого типа на текущем стенде и используй результат повторно.
После смены провайдера, tool mode, шаблона или настройки, меняющей динамическую схему,
перечитай фактическую схему узла. Примеры — сведения о проверенных версиях,
не универсальные запреты на существование других компонентов.
В Offline без снапшота допускается архитектурный черновик с кандидатами из справочника:
пометь типы/порты как неподтверждённые и перечисли, что сверить после подключения.

## Выполнение

1. **Точечная правка:** прочитай актуальный флоу, кратко назови изменение, примени
   минимальный patch и проверь затронутое поведение. Не пересобирай скелет.
2. **Простая новая цепочка:** короткий план, проверка схемы и spec, создание, запуск.
3. **Сложная сборка:** начни с минимального полезного пути и добавляй зависимости
   в порядке архитектуры. Проверяй смысловые этапы, откатывай только неудачный этап.
   Фиксированный порядок «модель → агент → БД» не обязателен.

Перед созданием проверяй spec:

```text
python scripts/validate_spec.py flow.spec --profile profiles/<стенд>
python scripts/validate_spec.py flow.spec --snapshot <снапшот.json> --format json
```

`E*` блокируют отправку. `W*` требуют оценки и объяснения существенных ограничений.
`--strict` делает предупреждения блокирующими. Exit: 0 — проверка пройдена,
1 — проблемы, 2 — ошибка чтения/снапшота. Коды: [spec-format.md](references/spec-format.md).
Валидатор проверяет имена, совместимость объявленных типов и обязательные поля,
когда снапшот знает дефолты. Старые/динамические схемы проверяются частично.
Он не подтверждает доступ к провайдеру, данным или смысл ответа.
Предпочитай серверную валидацию. `validate: false` используй для намеренно
промежуточного графа, который затем проверишь отдельно.

При полной замене сохрани исходный экспорт и перечитай состояние перед записью:
`update_flow_from_spec` заменяет граф и может потерять конкурентные правки.
Для боевого флоу используй копию, если задача не требует править оригинал.
Откат восстанавливает checkpoint, а не приблизительно воссозданную spec.
При запросе «поменяй только X» сравни полный граф до/после: успешный ответ сам по себе
не доказывает сохранность IDs, связей, credential-привязок и незатронутых полей.
Успех — ожидаемый результат на тестовом входе после последней правки.
Для памяти проверь несколько сообщений с одним `session_id` и изоляцию другой сессии;
для ветвления — обе ветки; для инструмента — фактический вызов, а не только ответ.
Учитывай внешние эффекты запуска, используй тестовые данные и разрешённые операции.
После структурных правок примени раскладку при необходимости; `notify_done` — если
доступен и нужен для обновления UI.

## Файлы, секреты и перенос

Для файлов обычно подходит Read File (`File` на проверенных стендах): загрузи файл
в хранилище целевого Langflow, свяжи с компонентом и проверь чтение нужных данных.
Для нестандартного формата выбери подходящий parser/компонент. Не подменяй документ
молча захардкоженным текстом. Поддержку форматов и таблиц проверяй на образце.
Экспорт графа не гарантирует перенос файлов. Перечисли файлы, переменные, расширения
и сервисы; загрузи файлы на новый стенд и перепривяжи компонент.

У поля модели может быть `value: OPENAI_API_KEY`, `load_from_db: true`.
Строковый config/`configure_component` способен снять привязку. Рабочую привязку сохраняй.
Для нового провайдера создай credential-переменную в настройках целевого Langflow
или через поддерживаемый API, привяжи её через UI/подтверждённый API переменных.
Если нужен REST patch графа, сохрани оригинал, измени только `value` на имя переменной
и `load_from_db: true`, затем перечитай и проверь запуск.
Не передавай literal-секрет в spec, отчёт, fixture или экспорт для передачи.
Не копируй креденшелы из произвольного рабочего флоу для тестов.

## Диагностика и отчёт

На проверенных стендах `run_flow` мог вернуть `False` без `isError`: это не успех.
Начни с фактического ответа `validate_flow`; если причины нет, используй build results
или build stream по API целевой версии. Не обобщай способ диагностики на все версии.
После трёх одинаковых неудач без новых данных останови повторные запуски и покажи
диагноз/недостающие сведения. Подробнее: [errors.md](references/errors.md).
В отчёте: что изменено, ссылка/ID флоу, проверки, как пользоваться, существенные
допущения, зависимости переноса и непроверенные возможности.
Не объявляй готовым то, что только прошло офлайн-валидацию.
