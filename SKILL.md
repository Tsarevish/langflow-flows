# Langflow: сборка цепочек

Ты собираешь рабочие флоу в Langflow. Не «текст, который выглядит как флоу», а граф,
который запускается и отвечает.

Автор скилла — **Andrey Datsenko**.

## Главное правило

**Ничего не пиши по памяти.** Имена типов, имена портов, имена полей и обязательность полей
зависят от версии и от установленных расширений. Перед каждым соединением — спроси сервер:
`describe_component_type`. Это не формальность: `OpenAIModel` не существует, а
`Prompt Template` пишется с пробелом.

## Режимы

Определи режим в первую минуту и скажи пользователю, в каком работаешь.

| Режим | Признак | Что доступно |
|---|---|---|
| **Live** | есть MCP-инструменты `mcp__langflow__*` (или REST к инстансу) | всё: сборка, валидация, запуск, диагностика |
| **Offline** | инстанса нет | только spec + JSON на импорт; проверки нет |

В офлайне **обязательно** предупреди одной фразой: «спека не проверена на инстансе».

## Шаг 0. Где строим

**Всегда спрашивай, в какой Langflow собирать флоу, прежде чем что-то создавать** —
особенно при новом флоу. Не угадывай по тому, к какому инстансу подключены инструменты.

Вопрос одним сообщением, с вариантами:

> Где собираем флоу?
> 1. **Локальный Langflow** (`http://127.0.0.1:7860`) — если он у тебя запущен.
> 2. **Удалённый сервер** — тогда пришли адрес и API-ключ.
> 3. **Офлайн** — соберу спеку, запустить и проверить не смогу.

Если выбран удалённый сервер и доступа ещё нет, попроси **два значения**:

- адрес с портом, например `http://10.0.0.5:7860` (или `https://langflow.example.com`);
- API-ключ Langflow: интерфейс → аватар → Settings → Langflow API → Add New.

Никогда не подставляй адрес и ключ из чужого профиля или из прошлой задачи молча.
Проверь доступ до сборки: `GET /api/v1/version` и один запрос под ключом.

## Шаг 0.5. Профиль стенда

Скилл общий, стенды разные. Всё установочное — версия, провайдеры, лимиты, запреты —
хранится в профиле `profiles/<стенд>/profile.md`, а не в правилах.

- Профиль есть → прочитай его разделы «Модели», «Ограничения», «Особенности».
- Профиля нет → сними: `python scripts/probe_stand.py`, затем дополни вручную по
  `references/recon.md`.
- Профиль устарел (версия не совпадает) → перегенерируй, имена компонентов меняются
  между версиями.

Без профиля работай по общим правилам и **скажи**, что профиль не снят: рекомендации
про лимиты и форматы будут догадкой.

## Рабочий процесс

Семь шагов. Гейты обязательны — они и есть ценность скилла.

### 1. Разведка
- Где строим (шаг 0) и профиль стенда (шаг 0.5).
- Что собираем: новый флоу или правим существующий.
- Правка существующего: сначала `get_flow_info`, потом план изменений.

### 2. Уточнение — обязательные вопросы

Спрашивай **до** первой спеки. Пропускать вопрос можно, только если ответ уже прозвучал
в задаче явно.

1. **Где строим** — локально или удалённый сервер, с адресом и ключом (шаг 0).
2. **Модель и её API.** Провайдер, `openai_api_base`, имя модели, откуда берётся ключ.
   Если профиль стенда уже знает рабочую модель — предложи её как вариант по умолчанию,
   но всё равно спроси. Не подставляй модель молча.
3. **Вход и выход:** чат в Playground, вызов по API, файл, таблица.
4. **Данные и файлы:** какой файл или источник участвует (см. ниже «Файлы»).

Плюс, если задача это допускает, — **выбор способа** (см. «Развилка решений»).

Мало ответов — задай остаток одним сообщением. Нет ответа вовсе — прими допущение,
**назови его вслух** одной строкой и двигайся дальше.

### 3. План на 5–7 строк
Список узлов, список соединений, что явно не делаем. Покажи пользователю.
Без подтверждения дальше — только если он сказал «делай».

### 4. Скелет
Минимальная цепочка: вход → смысловой центр → выход. Обычно 3 узла.
- проверь типы через `describe_component_type`
- **прогони офлайн-валидатор** (см. ниже) — он ловит опечатки в типах и портах за секунду
- создай через `create_flow_from_spec` c `validate: false` (см. «Ловушки»)
- запусти: `run_flow` с осмысленным входом

**Гейт:** пока скелет не ответил — не добавляй ни одного узла.

### 5. Наращивание по одному
Порядок: промпт → модель → агент → инструменты → память → БД/файлы → ветвления.
После каждого шага — `run_flow`. Сломалось — откати этот шаг, не весь флоу.

### 6. Доводка
- `layout_flow` — если добавлял/удалял узлы (после `create_flow_from_spec` раскладка уже есть).
- Явно задай поля, влияющие на поведение: модель, температура, лимит токенов, формат вывода.
- `notify_done` — чтобы UI обновился.

### 7. Сдача
Отчёт по шаблону:

```
Собрано: <что>, узлов N, связей M
Проверено: запуск — да/нет, что вернул
Решения: <2–3 строки: почему так>
Не выбрано: <какие варианты предлагал и почему остановились на этом>
Не проверено: <честно>
Как пользоваться: Playground / API / что нажать
```

## Файлы и данные

**Любой файл, который участвует во флоу, подключается блоком `File` (Read File)**
с загрузкой в поле `Files` — если пользователь явно не попросил другой способ.

Что это значит на практике:

- содержимое файла не вставляется текстом в промпт — в промпт идёт выход блока `File`;
- не читаем файл внешним скриптом «сбоку» и не хардкодим путь в поле;
- не просим пользователя копировать текст документа в чат.

Почему так: файл живёт в сессии/флоу, путь не ломается при переносе, флоу воспроизводим
и его можно отдать другому человеку.

Исключения — только по прямой просьбе пользователя:

- «вставь текст прямо в промпт» (короткий документ, без файла);
- «прочитай файл скриптом» (нет блока `File`, нестандартный формат);
- данные приходят не файлом, а из API или базы.

Что сказать при выборе: **рекомендую `File`**, потому что так флоу переносим. Если
пользователь против — делаем как он, но фиксируем это в отчёте.

Подводные камни: после импорта флоу файл нужно выбрать заново (`No files to process`);
xlsx, pptx и сканы требуют Advanced Parser (есть не везде); таблицы внутри docx
`File` теряет. Актуальные ограничения — в профиле стенда.

## Развилка решений

Если задачу можно собрать разными способами — **спроси, но с рекомендацией**.
Не решай молча и не выкладывай пять равноправных вариантов.

Формат: рекомендуемый первым, у каждого — одна строка последствий.

> Как собираем ответ по базе?
> **(рекомендую) Агент сам пишет SQL** — 6 узлов, быстро; риск: модель ошибётся в запросе.
> Б. Сначала показываем SQL пользователю, выполняем после подтверждения — надёжнее,
> но на два узла больше и нужен `Human Input`.

Типичные развилки, где надо спрашивать:

| Развилка | Рекомендация по умолчанию |
|---|---|
| агент или цепочка «промпт + модель» | цепочка, если нет инструментов: дешевле и предсказуемее |
| SQL напрямую или с подтверждением | напрямую для чтения, с подтверждением для записи |
| RAG или файл целиком в промпт | файл целиком для короткого документа, RAG — для большого |
| один агент или цепочка ролей | цепочка ролей, если шаги всегда в одном порядке |
| инструмент готовый или свой компонент | готовый; свой — только если прав не жалко |

Правило: одна развилка — один вопрос. Не смешивай его с уточнением модели и файлов.

## Офлайн-валидатор

Проверяет спеку без обращения к серверу — по снапшоту схем компонентов.

```
python scripts/validate_spec.py flow.spec
python scripts/validate_spec.py flow.spec --strict        # предупреждения = ошибки
python scripts/validate_spec.py flow.spec --format json   # для программной обработки
python scripts/validate_spec.py flow.spec --profile profiles/<стенд>
```

Снапшот берётся из профиля стенда. Если профилей несколько, укажи `--profile`
или задай `LANGFLOW_PROFILE`.

Код возврата: 0 — чисто, 1 — не пройдено, 2 — нет файла/снапшота.

| Код | Что значит |
|---|---|
| E001 | нет ни одного узла |
| E002 | сломанная строка: раздел, узел, связь, config |
| E003 | узел объявлен дважды |
| E004 | неизвестный тип компонента (с подсказкой ближайшего) |
| E005 | связь ссылается на несуществующий узел |
| E006 / E007 | нет такого выхода / входа (часто — стороны связи перепутаны) |
| E008 / E009 | config ссылается на несуществующий узел / поле |
| E010 | секрет записан в поле-переменной — сломает авторизацию |
| E011 | соединено в порт, которого нет в шаблоне промпта |
| W001 | переменная в шаблоне ни к чему не подключена |
| W003 | у агента нет модели |
| W004 | у ветвления подключён только один выход |
| W005 / W008 | нет выхода / от входов нет пути до выхода |
| W006 | секрет в открытом виде в обычном поле |
| W009 | у SQL не задана строка подключения (защищённое поле) |

**Правило:** `E*` — почти наверняка падение, исправляй до отправки.
`W*` — запустится, но поведение не то; о каждом предупреждении скажи пользователю.

Валидатор не заменяет запуск: он проверяет структуру, а не смысл. Прогон всё равно нужен.

## Ловушки (проверено на инстансе)

**1. Секреты нельзя задавать через `configure_component` и в spec.**
Поле `api_key` у модели по умолчанию привязано к переменной: `load_from_db: true`.
Если записать туда `OPENAI_API_KEY` — Langflow сохранит **строку** и снимет привязку.
Итог: `AuthenticationError ... Unknown api key`. Правильно: **не трогать поле вообще**.
Сломалось — вернуть `load_from_db: true` через `PUT /api/v1/flows/{id}`.

**2. Диагностика зависит от версии.**
`run_flow` при падении возвращает буквально `False` — без причины, на любой версии.
`validate_flow` на 1.12 отдаёт общее `{"valid": false, "errors": [{"error": "Build error"}]}`,
а на 1.13 называет узел и причину (`Error building Component OpenAI: … variable not found`).
Если версия из профиля — 1.12 или старше, причина лежит только в build-стриме:
`POST /api/v1/build/{flow_id}/flow?log_builds=true&event_delivery=direct`,
события NDJSON, причина в `data.data.content_blocks[].contents[].reason`. См. `references/errors.md`.

**3. Вход у `Prompt Template` появляется от переменной в шаблоне.**
Пока в шаблоне нет `{question}`, у узла `inputs: []` и соединять некуда.
Порт называется ровно как переменная: `A.message -> P.question`.

**4. `create_flow_from_spec` с `validate: true` (по умолчанию) не создаёт флоу при ошибке.**
Для сборки по шагам — `validate: false`, проверка отдельно.

**5. Защищённые поля не переопределяются через `tweaks`.**
`run_flow(tweaks=...)` отказывает: «The field is protected and keeps the value set by the flow
author». Такие поля (например `database_url` у SQL) правятся только в самом флоу.

**6. Изменения через API не исполняются сами.**
Правки структуры — это сохранение. Исполнение — только `run_flow`/`build_flow`.

**7. У модели два выхода, и они не взаимозаменяемы.**
`text_output` («Model Response») выполняет запрос и отдаёт текст; `model_output`
(«Language Model») модель не вызывает, а передаёт её настройки агенту. Если подключить
агенту не тот выход, он возьмёт модель по умолчанию — и вернётся ошибка провайдера,
будто дело в ключе или регионе.

**8. Лимиты и запреты — из профиля, а не из головы.**
Предел времени на запуск, число одновременных запросов к модели, разрешение на запись
файлов, читаемые форматы, доступ в интернет — у каждого стенда свои. Смотри
`profiles/<стенд>/profile.md`. Если профиля нет, спроси у человека, а не угадывай:
дорогой флоу, обрывающийся на середине, — типичное следствие такого угадывания.

## Чего не делать

- Генерировать JSON графа руками: `sourceHandle`/`targetHandle` — закодированные строки
  с разделителем `œ`. Только spec или инструменты.
- Строить сразу «полный» флоу с RAG, памятью и четырьмя инструментами.
- Молча менять модель, промпт или температуру в чужом флоу.
- Оставлять дефолты в полях, влияющих на поведение.
- Объявлять готовым без запуска. Не запускал — так и напиши.
- Перезаписывать флоу, который пользователь правит в UI: сначала `get_flow_info`,
  потом скажи, что изменения из UI могут потеряться.
- Начинать сборку, не выяснив, **где** её делать, и молча подставлять модель,
  адрес или ключ из прошлой задачи.
- Вставлять содержимое файла в промпт текстом, если пользователь не просил именно так.
- Выбирать один из нескольких разумных способов молча — спрашивай, рекомендуя.
