# Процесс подробно

Расшифровка шагов из `SKILL.md`. Читай, когда задача сложнее «собери чат с моделью».

## Шаг 0. Где строим

Спрашивай всегда, когда создаёшь новый флоу. Даже если MCP-инструменты уже подключены
к какому-то инстансу: «подключены» не значит «здесь и надо».

Формулировка, которая работает:

> Где собираем флоу?
> 1. Локальный Langflow (`http://127.0.0.1:7860`).
> 2. Удалённый сервер — пришли адрес и API-ключ.
> 3. Офлайн — соберу спеку, но не запущу.

Для удалённого сервера нужны **адрес с портом** и **API-ключ**
(интерфейс → аватар → Settings → Langflow API → Add New). Проверь до сборки:
`GET /api/v1/version` отвечает, `GET /api/v1/flows/` под ключом возвращает 200.
Ключ не принят — скажи прямо, а не собирай наугад.

Адрес и ключ не переиспользуй из чужого профиля или предыдущей задачи: другая
установка — другой ключ, другие компоненты, другой профиль.

## Шаг 1. Разведка

Что выяснить до первой спеки:

| Вопрос | Как |
|---|---|
| Где строим | спросить (шаг 0) |
| Профиль стенда есть? | `profiles/*/profile.md`; если нет — `scripts/probe_stand.py` |
| Версия инстанса | профиль; иначе `GET /api/v1/version` |
| Какая модель доступна | профиль, раздел «Модели»; иначе `GET /api/v1/models` |
| Что нельзя | профиль, раздел «Ограничения» |
| Есть ли рабочий флоу для сверки | `list_flows`, искать что-то живое |
| Не суперюзер ли | `GET /api/v1/users/whoami` |
| Чем занят флоу сейчас | `get_flow_info` перед любой правкой |

Если версия отличается от той, на которой снимался профиль, — перегенерируй профиль:
часть фактов (`create_flow_from_spec`, `layout_flow`, `load_from_db`) привязана к версии,
и на другой версии поведение может отличаться.

## Шаг 2. Уточнение

Четыре обязательных вопроса плюс развилка способа, если она есть.

**1. Где строим** — см. шаг 0.

**2. Модель и её API.** Спрашивай даже при наличии профиля: у человека может быть
свой ключ или другая модель.

> Какую модель берём? В профиле стенда рабочая — `<имя>`, адрес `<base>`,
> ключ в переменной `OPENAI_API_KEY`. Оставляем её или другую?

В отчёт запиши: провайдер, `openai_api_base`, `model_name`, откуда ключ.

**3. Вход и выход:** чат в Playground, вызов по API, файл, таблица.

**4. Данные и файлы:** файл, база, внешний API или ничего. Файлы — только через
блок `File` (см. раздел «Файлы и данные» в `SKILL.md`).

Плохие вопросы: «какой хотите функционал?», «расскажите подробнее».
Хорошие: выбор из двух-трёх вариантов с последствием.

Пример правильного уточнения:

> Собираю агента, который отвечает по базе. Два варианта:
> **(рекомендую) А.** агент сам формирует SQL, запрос идёт в БД напрямую — 6 узлов,
> быстро; риск: модель ошибётся в запросе.
> **Б.** сначала показываем запрос пользователю, выполняем после подтверждения —
> надёжнее, но плюс `Human Input` и два узла. Какой?

Если пользователь молчит — выбери рекомендуемое, назови это одной строкой и иди дальше.

## Шаг 3. План

Формат, который читается за пять секунд:

```
План:
1. ChatInput → Agent (промпт: правила ответа)
2. Модель → Agent.model
3. Agent.response → ChatOutput
Не делаем: память, инструменты, БД. Добавим отдельным шагом, если понадобится.
```

Показывай всегда, кроме случая «пользователь сказал делай сразу».

## Шаг 4. Скелет

1. `describe_component_type` для каждого узла из плана — выпиши себе **точные** имена.
2. Спека минимальная. `validate: false`.
3. `get_flow_info` — убедись, что узлы и связи на месте.
4. `run_flow` с осмысленным входом.

Что считать успехом скелета: получен непустой ответ, и он по смыслу соответствует
запросу. «Запустилось без ошибки» — не успех.

## Шаг 5. Наращивание

По одному элементу, в этом порядке:

1. системный промпт (правила поведения);
2. модель (если её не было в скелете);
3. инструменты;
4. память и сессии;
5. БД, файлы, внешние API;
6. ветвления и обработка ошибок.

После каждого — `run_flow`. Не сработало — откат **этого** шага:

```
update_flow_from_spec(flow_id, спека без последнего элемента)
```

Полная пересборка с нуля теряет контекст и время.

## Шаг 6. Доводка

Чек-лист перед сдачей:

- [ ] ни в одном значимом поле не остался дефолт (модель, температура, лимит токенов, формат);
- [ ] секреты не вписаны руками в поля, привязанные к переменным;
- [ ] `layout_flow` после добавлений/удалений;
- [ ] у `ConditionalRouter` подключены оба выхода;
- [ ] `notify_done` вызван;
- [ ] флоу запускается после всех правок, а не только после первой.

## Шаг 7. Сдача

Шаблон отчёта:

```
Собрано: агент, который отвечает по базе (6 узлов, 5 связей)
Проверено: запуск — да. На вопрос «сколько таблиц в схеме public» вернул: 1
Решения: модель через Yandex-шлюз (OpenAI из этого региона недоступен);
         агент возвращает чистый SQL — так убрали хрупкую регулярку
Не проверено: многострочные SQL и ошибки прав доступа
Дальше: открыть в Playground / вызвать по API / что нажать
```

«Не проверено» — обязательная строка. Пустая — значит неправда.

## Правка существующего флоу

1. `get_flow_info` — что есть.
2. Скажи пользователю, что меняешь, и предупреди: **правки в UI во время работы
   будут потеряны** (инструменты перезаписывают граф целиком при `update_flow_from_spec`).
3. Для точечных изменений — `configure_component` / `connect_components`, не полная замена.
4. Для структурных — `update_flow_from_spec`, затем `run_flow`.
5. `notify_done`.

Если флоу чужой или боевой: сначала `duplicate_flow`, потом правь копию. Это дешевле,
чем объяснять, почему сломался рабочий сценарий.

## Когда остановиться

- Нужен ключ или провайдер, которого нет в инстансе.
- Нужен кастомный компонент, а прав не хватает.
- Три раза подряд одна и та же ошибка — покажи диагноз и спроси.
- Запрос требует узла, которого нет в этой версии.
- Пользователь просит «сделать красиво» без критерия — предложи два конкретных варианта.
