# Интеграционные проверки готовых spec

Набор проверяет работу заданных графов, а не самостоятельное решение задачи агентом.
Независимая оценка инструкций — ../behavior/README.md.
Исторический результат 12/12 от 13.11.2026 относится к прежней, более слабой методике.
Live-прогон от 14.11.2026: по 11/12 на двух стендах; SQL заблокирован окружением.
Подробности и ограничения — [LIVE_RESULTS.md](LIVE_RESULTS.md).

## Настройка

Python 3.10+ и стандартная библиотека; внешние tools-модули не нужны.
Сначала сними профиль тестового стенда. Явно задай окружение:

- LANGFLOW_URL (или LANGFLOW_SERVER_URL) — целевой стенд;
- LANGFLOW_API_KEY — доступ к стенду;
- LANGFLOW_EVAL_MODEL_BASE и LANGFLOW_EVAL_MODEL_NAME — API base и модель;
- LANGFLOW_EVAL_CREDENTIAL — имя уже настроенной credential-переменной, не ключ;
- LANGFLOW_EVAL_MODEL_TYPE — необязательно, тип совместимой модели вместо типа из образцов;
- LANGFLOW_EVAL_DATABASE_URL — только для SQL-сценария, выделенная тестовая БД
  с пользователем только для чтения. SQLite на проверенных стендах запрещена,
  даже в памяти; не отключайте защиту ради теста.

Можно использовать защищённый локальный --env-файл с этими значениями.
Не добавляй его в репозиторий. Код не извлекает подключения из рабочих флоу.
Перед live-проверкой сверяются целевой URL, версия снапшота и наличие переменной.

```text
python tests/run_eval.py --check-only --profile profiles/<стенд>
python tests/run_eval.py 01 --live --profile profiles/<стенд>
python tests/run_eval.py --live --profile profiles/<стенд>
```

--check-only не делает сетевых запросов/изменений. Модельные сценарии требуют
подстановки имени и API base даже в этом режиме. Для 01 они не нужны.
Без --live запуск с побочными эффектами невозможен. --json оставлен совместимым
флагом: вывод всегда JSON, сообщения конфигурации — stderr.

## Критерии

Для SQL используется запрос SELECT 7 AS eval_value, 11 AS eval_other без таблиц;
он не требует чтения рабочих данных. Результат должен содержать оба поля и значения.

Проверяются исходная и итоговая spec. Для успеха нужны: отсутствие ошибок валидатора,
создание, обновление (если нужно), все запуски, ожидаемые ответы, доказательства
поведения и удаление временного флоу. False/пустой ответ не считаются запуском.
Удаление выполняется в finally; при сбое отчёт содержит ID оставшегося флоу.

Память (07): запись факта, извлечение в той же сессии, изоляция другой сессии.
Ветвление (09): положительный/отрицательный вопрос и уникальная sender_name-маркировка
выходных ChatOutput. Инструменты (06/12): завершённый tool_use текущего run с output.status=success,
а не упоминание имени/правильный ответ. Build results используются лишь при совпадении
run_id: старый trace не доказывает текущий вызов. Если сервер не отдаёт подходящий
trace, evidence=false; тест не засчитывается, даже если число правильное.

Ответы модели недетерминированы. Тестовые session IDs уникальны; сервер может хранить
историю/логи после удаления графа. Используй выделенное тестовое окружение и его
обычную политику очистки, runner не удаляет общие сообщения или ресурсы.


Для сохранения обезличенных ответов добавьте `--artifact-dir <каталог>`.
Отчёт содержит ID графа и сессий, ответ и итог каждой проверки. Тестовая обвязка
не засчитывает одиночный tool_calls-запрос модели без успешного выполнения инструмента.
Обычные false-флаги метаданных не означают сбой; корневой False и явные error/valid=false — означают.
