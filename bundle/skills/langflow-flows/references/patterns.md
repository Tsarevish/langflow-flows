# Типовые цепочки

Восемь паттернов от простого к сложному. Порядок — рекомендуемый порядок изучения и сборки.
Отметка «проверено» значит: собрано на инстансе и запущено.

---

## 1. Эхо (проверено)

```
ChatInput → ChatOutput
```
Проверка, что инстанс и инструменты живы. Возвращает ровно введённый текст.
Занимает 1 запрос. Любую работу начинай с него, если инстанс незнакомый.

## 2. Чат с моделью (проверено)

```
ChatInput → Модель → ChatOutput
ChatInput.message → Модель.input_value
Модель.text_output → ChatOutput.input_value
```
Минимум для «здравствуй, LLM». Адрес модели и её имя берутся из профиля стенда.

## 3. Промпт-чейн (собрано)

```
ChatInput → Prompt(шаблон с {question}) → Модель → ChatOutput
ChatInput.message → Prompt.question
Prompt.prompt     → Модель.input_value
```
Смысл: правило живёт в отдельном узле, его видно и можно менять без правки агента.
Не забыть: порт называется как переменная.

## 4. Агент с правилами (проверено)

```
ChatInput ─→ Agent.input_value
Prompt(правила) → Agent.system_prompt
Модель → Agent.model
Agent.response → ChatOutput
```
Четыре узла вокруг агента. `Agent.max_iterations` поднять до 10–15, если задача
многошаговая. Промпт-узел удобен тем, что правила версионируются отдельно.

## 5. Агент + база данных (проверено)

```
ChatInput → Agent(← Prompt, ← Модель) → SQLComponent → ChatOutput
Agent.response → SQL.query
SQL.run_sql_query → ChatOutput.input_value
```
Работает, если агент возвращает **чистый SQL**: без markdown-блоков, без пояснений,
без точки с запятой. Это гарантируется системным промптом, а не надеждой.

Проверенный промпт (сокращённо):
> Верни ТОЛЬКО SQL-запрос для PostgreSQL: без пояснений, без markdown-блоков,
> без точки с запятой в конце.

`database_url` — защищённое поле: `tweaks` его не меняет, значение живёт в флоу.
Это же значит, что строку подключения нельзя передать снаружи — только хранить в флоу
(и следить, чтобы она не утекла в git).

Ограничение: если модель всё же обернёт SQL в ```sql — узел упадёт. Тогда нужен
извлекающий узел (см. паттерн 6 или `Operations` с `Text Extract`).

## 6. Ветвление по маркеру (собрано, не прогонялось)

```
Agent.response → ConditionalRouter.input_text
Router.true_result  → SQL.query        (если в ответе есть маркер)
Router.false_result → ChatOutput        (иначе — уточняющий вопрос)
```
Классическая схема «сначала договорились, потом выполнили»: агент пишет `SQL_READY:`
и запрос, роутер по `contains` решает, идти в БД или переспросить.
Маркер и `operator` — поля роутера; `match_text` тоже можно подать входом.

Оба выхода роутера обязаны быть подключены.

## 7. RAG (не проверено)

```
File / Knowledge Base → Splitter → Embeddings → Vector Store
                                        ↓
ChatInput → Retriever → Prompt(контекст + вопрос) → Модель → ChatOutput
```
Порядок сборки: сначала вектор-стор и загрузка документа, потом retriever, потом промпт.
Проверять по шагам: сначала «сколько чанков загрузилось», потом «что вернул retriever»,
и только потом — ответ модели. Иначе непонятно, где пусто.

## 8. Несколько агентов (не проверено)

```
ChatInput → Router (по интенту) → Агент A / Агент B → общий ChatOutput
```
Правило: у каждого агента свой промпт и своя модель, общий только выход.
Не строить, пока не работает один агент.

---

## Как выбирать

| Задача | Паттерн |
|---|---|
| проверить связку с инстансом | 1 |
| «просто чат с LLM» | 2 |
| нужен управляемый системный промпт | 3 или 4 |
| агент должен что-то делать с данными | 5 |
| нужен диалог с подтверждением шага | 6 |
| ответы по своим документам | 7 |
| разные сценарии в одном флоу | 8 |

## Общее правило роста

Скелет (1–2) → один смысловой узел (3–4) → действие (5) → управление (6) → знания (7).
Никогда не перескакивай: ошибка в основе маскируется под ошибку в настройке.

## Из курса: связки, которых нет выше

Ключи (c1, d1…) — из `course-flows.md`, там же готовые соединения.

### Диалог с памятью (d1)
```
Memory.messages_text → Prompt.history
Prompt.prompt        → Model.system_message
ChatInput.message    → Model.input_value
Model.text_output    → ChatOutput
```
Сообщения сохраняют сами Chat Input и Chat Output — отдельный блок «Store» не нужен.
Память видит только эту сессию и этот поток.

### Цикл по таблице (c1)
```
SplitText/File → Loop.data
Loop.item → Parser → Prompt → Model
Model.text_output → Loop.∞      (обратно в цикл!)
Loop.done → Parser → ChatOutput
```
Без связи в порт `∞` тело цикла не запустится, а ошибки не будет. Прервать рано нельзя.
`item` — это Data: в промпт только через Parser.

### Цикл с возвратом (c2, n9)
```
Точка возврата (свой блок с портом ∞) → Prompt → Model
Model → проверка (модель или код) → If-Else
If-Else.false_result → Точка возврата
If-Else.true_result  → ChatOutput
```
Прямая обратная связь «If-Else → промпт» вешает поток: нужен блок с портом цикла.

### Подтверждение человеком (b3)
```
Model.text_output → HumanInput.prompt
HumanInput.branch_approve → ChatOutput «отправлено»
HumanInput.branch_reject  → ChatOutput «на доработку»
```
Пока решения нет, ветки пусты — это норма. Внутри подпотока не работает.

### Таблица построчно (e2)
```
TypeConvert(auto_parse) → BatchRun.df
Model.model_output      → BatchRun.model
BatchRun.batch_results  → Parser → ChatOutput
```
Один блок вместо цикла. Сбой по строке рушит весь блок.

### Поля из текста (e1)
```
ChatInput → StructuredOutput.input_value
Model.model_output → StructuredOutput.model
StructuredOutput.dataframe_output → Parser → ChatOutput
```
Если полей несколько объектов — на выходе `results`, поэтому берётся выход Table.

### Агент с MCP-инструментами (d4)
```
MCPTools (Tool Mode) → Agent.tools
Model.model_output   → Agent.model
```
Сервер MCP добавляется в Settings; пустой список инструментов = сервер недоступен
с самого Langflow.

### Подпоток (f2)
```
RunFlow (выбрать поток) → поля его входов появляются на блоке
```
Ошибка внутри — общей фразой; причину смотреть запуском подпотока отдельно.
