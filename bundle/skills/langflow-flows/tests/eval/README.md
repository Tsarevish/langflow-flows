# Eval-набор

12 сценариев против живого Langflow. Цель — не «красиво», а измеримо:
собирается ли цепочка с первого прохода и отвечает ли она то, что обещано.

## Запуск

```
python tests/run_eval.py          # все сценарии
python tests/run_eval.py 05 09    # выборочно
python tests/run_eval.py --json   # машинный формат (сводка уходит в stderr)
```

Каждый сценарий проходит путь скилла:

1. офлайн-валидатор (ошибки/предупреждения до отправки);
2. `create_flow_from_spec` с `validate: false`;
3. для правок — `update_flow_from_spec`;
4. `run_flow` с осмысленным входом;
5. сверка ответа с ожидаемым;
6. удаление флоу.

Перед запуском сценариев со SQL строка подключения подставляется из рабочего флоу владельца —
в файлах она не хранится.

## Фактические ответы

Прогон читается глазами, а не только регулярками: в проверке сверки участвовали
«Париж», «42», «Толстой», таблица `table_count = 1`, «391», «Tokyo», «да», «нет»,
«готово», «12». Регулярки после этого ужесточены (`\b391\b` вместо `391`,
`\b(да|yes)\b` вместо `да`), чтобы не ловить подстроки вроде «данные».

## Чего в наборе нет

- **RAG**: ретривер, векторное хранилище, эмбеддинги. На инстансе нет проверенного
  эмбеддера (доступен только ключ Yandex-шлюза), поэтому сценарий честно исключён,
  а не заменён суррогатом.
- **Кастомные компоненты** — путь не проходил.
- **Ошибки прав доступа к БД** и многострочные SQL.
- **Повторяемость**: ответы модели недетерминированы; часть сценариев может
  изредка не совпасть по формулировке. Регулярки это допускают, но не гарантируют.

## Ограничение методики

Спеки для набора писал тот же агент, который писал скилл, уже зная имена компонентов.
Это завышает результат: настоящая проверка — дать сценарии человеку, который скилл
не видел, или запустить агента с нуля на формулировке задачи, без готовой спеки.
Пока набор меряет «собирается ли по правилам скилла», а не «помогает ли скилл думать».
